## Implementation

Added `ReminderApplier.reconcile(desiredPlan, platform, payloadVariant,
readPendingPlatformIds: ...)` in `lib/data/reminders/reminder_apply.dart`.
It uses the existing applier queue shared with `apply`/`applyDiff`, validates
the opaque variant and duplicate desired IDs, loads the ledger, then queries
and copies the pending OS IDs while still inside the queue. Validation, ledger
load, and query errors occur before any platform call or ledger write; a query
error is propagated rather than interpreted as an empty pending list, and the
queue remains usable afterward.

Reconciliation leaves an exact applied-metadata/variant entry alone only if
its reserved ID is pending. It repairs missing, changed, or stale-variant
entries under their existing IDs; cancellations and cancellation-record
writes precede all schedules. A failed cancel or cancellation record blocks
only that job's replacement. Removed applied work is cancelled idempotently.
A pending bare reservation is treated as an orphan: it is cancelled before a
desired retry, or cancelled alone when undesired; no applied metadata is
invented, and a successful orphan cancellation is reported. An absent bare
reservation remains untouched. Unregistered OS IDs are not cancelled or
assigned guessed jobs; if a new monotonic allocation would collide with a
pending unregistered ID, that job is reported as failed rather than overwriting
it. Reservations, storage key/schema, public result types, `ReminderPlatform`,
`apply`, and `applyDiff` remain unchanged.

No plugin imports, permissions, filesystem/network access, clock reads,
catch-up alerts, or intent mutations were added. No production activation or
plugin wiring is included.
