## 1. Reproduction (before the fix)

A `ValueNotifier` listener runs **synchronously** inside `notifyListeners`, and
`refresh()` used to register the in-flight future only *after* `_runRefresh()`
had already emitted the loading state:

```dart
return _inFlight = _runRefresh();   // _runRefresh() emits isLoading:true first
```

So a listener that reacted to `isLoading == true` by calling `refresh()` (a
retry banner, a pull-to-refresh controller reacting to state) started a *second*
attempt before the first future existed. One test reproduces it with a one-shot
listener — no recursion:

```dart
void listener() {
  if (triggered) return;                       // one-shot
  if (!repo.state.value.isLoading) return;
  triggered = true;
  listenerRefresh = repo.refresh();            // re-enters from the notification
}
```

(`flutter test test/data/reentrant_refresh_test.dart`):

Two distinct defects surfaced, both in the brief's scope:

1. **Duplicate attempt** — the single-flight window opened too late.
2. **Disposal from a listener was illegal** — Flutter asserts when a
   `ChangeNotifier` is disposed during its own `notifyListeners`, so
   `dispose()` from a state callback blew up before it could stop the attempt.
   A third: a listener retry after an error silently joined the *finished*
   attempt (`Expected: <2>, Actual: <1>`), and a pending `refresh()` future never
   completed when disposal happened.

## 2. Fix

`refresh()` now opens the window synchronously, before any notification:

```dart
final attempt = Completer<void>();
_attempt = attempt;            // registered first
_inFlight = attempt.future;
_startAttempt(attempt);        // emits loading afterwards
return attempt.future;
```

* `_startAttempt` wraps `_runRefresh` in `try/catch/finally`; `_release` closes
  the window exactly once, so the marker can never stay stuck (including after a
  provider that throws synchronously).
* `_release` uses an identity check, so a newer attempt started from a terminal
  notification is not cleared by the attempt that is finishing.
* The terminal (success/error) state is published **after** `_release`, so a
  listener that retries from an error banner starts a real new attempt. A
  listener that calls `refresh()` on the *loading* state still joins the running
  attempt (one transport call, one cache write).
* `_runRefresh` checks `_disposed` right after **each** emission and await:
  after the loading emit, after the cache read, after the fetch+validation and
  after the cache write. That is what stops a fetch or a new cache write from
  starting after disposal.
* `dispose()` releases the in-flight attempt first (pending `refresh()` futures
  complete instead of hanging), then disposes the internal notifier **one
  microtask later**. Leaving the synchronous stack is required by Flutter's
  `_notificationCallStackDepth == 0` assertion and makes
  "dispose from a listener" legal. No state can slip out in between because
  `_disposed` is already set and `_emitState` returns early.
* `dispose()` stays idempotent; `refresh()` after disposal still returns a
  completed future and does no work.

Constructors and contract signatures are unchanged
(`CachedJobRepository({required this._transport, required this._cache})`),
`JobFeedState`/`JobRepository` are untouched, and no dependency was added
(`dart:async` is part of the SDK).

## 3. Truthful lifecycle limits (what is *not* cancelled)

* **An already-started platform write is not recalled.** If `dispose()` lands
  while `FeedCache.write()` is in flight, that write runs to completion; the
  repository only guarantees it will not *publish* the result and will not
  *begin* another write. Cancelling a write mid-flight is not possible through
  the `FeedCache` interface, and a half-applied write cannot be "undone" without
  inventing schema/rollback policy, which this brief excludes.
* **An in-flight transport call is not aborted.** `dispose()` stops the
  *attempt*; the provider's future may still resolve later. Its bytes are
  ignored (`_disposed` is checked before parse/cache/publish). `HttpFeedTransport`
  has no abort API on a caller-owned `http.Client` (documented in A2), so this
  cannot be tightened from here.
* **The notifier is disposed one microtask after `dispose()` returns its
  future.** Anything holding `repository.state` after `await dispose()` sees the
  last published value; the object is inert (no listener runs again).
* Semantics kept from batch 1: `lastError` remains one of the fixed user-safe
  strings; nothing here reclassifies transport failures or invents offline data.

## 5. Integration notes for the captain

1. **Order at shutdown:** `await repository.dispose()` before closing the
   injected `http.Client`; a fetch that resolves after disposal is ignored, but
   closing the client first would turn it into a spurious transport error.
2. **Retry UI is now safe to drive from the state callback.** A widget that calls
   `repository.refresh()` from an error banner gets a genuine new attempt; one
   that calls it from the loading state is coalesced. Both were previously
   possible sources of duplicate requests or dead retries in the production shell.
3. **`dispose()` from a widget listener is now supported** — e.g. a screen that
   disposes its scope when the feed flips to a terminal state will no longer
   trip Flutter's notifier assertion.
4. Nothing in this batch changes how the production shell constructs the
   repository; no wiring is required beyond the ordering in (1).
