## What changed

### Link validation + launch guard (`lib/features/common/external_link.dart`, new)

- `validateExternalLink(String)` → `LinkCheck` (`.valid(uri)` / `.invalid(rejection)`).
  Accepted only when the raw string is **unchanged** (no leading/trailing whitespace, no control
  characters, no padding), parses as an absolute URI, scheme is exactly `https`, host is non-empty,
  `userInfo` is empty and there is **no fragment**. No normalisation, no scheme repair: a rejected
  `http://` URL is never rewritten into `https://`, and the accepted `Uri` is the feed's own string.
- Rejection reasons are distinct: `malformed`, `unsafeCharacters`, `notHttps`, `missingHost`,
  `embeddedCredentials`, `fragment`. Scheme is tested directly because `Uri.isAbsolute` is `false`
  whenever a fragment is present; fragments are then rejected explicitly.
- `ExternalLinkGuard` — one instance per detail screen: a `Set<String> _pending` of URLs.
  `open({actions, rawUrl}) → LinkOpenStatus` (`opened` / `invalid` / `failed` / `duplicate`)
  validates **before** touching `AppActions`, suppresses a second call for a URL already pending,
  catches both synchronous throws and async rejections, and always clears the pending entry in
  `finally`. `AppActions` interface is unchanged; no WebView, no new dependency.

### Job detail (`lib/features/job_detail/job_detail_screen.dart`)

- `_links` guard + `_pendingLink` state. `_open` validates, then `if (!mounted) return` before any
  `setState` or snackbar; invalid → localized `K.linkUnsafe`; failed → `K.linkOpenFailed`;
  duplicate → silent. A launcher finishing or throwing after disposal touches nothing.
- `_OfficialLinks` takes `pendingUrl` and disables only the button whose URL is in flight, showing
  an inline spinner label — the other link stays usable and unrelated writes are unaffected.
- The source-verification disclaimer is retained verbatim; notice/source/apply all pass through the
  same guard.

### Truthful reminder copy and states (`strings.dart`, `reminder_controller.dart`)

- New outcome `ReminderOutcome.permissionError`, distinct from `permissionDenied` (the permission
  channel threw) and from `failed` (storage write failed). Messages:
  - enabled: "request saved for 24 hours before the deadline … this is a saved request only — no
    notification is confirmed" (no scheduled/delivered claim);
  - disabled: "request removed" (no OS-cancellation claim);
  - denied: permission not granted, nothing saved;
  - permission error: permission state could not be checked, nothing saved;
  - failed: save failed, previous state unchanged;
  - closed / no deadline: unchanged truthful states.
- `reminderPolicyHelp` (detail panel) and `reminderSheetPolicy` (home reminder sheet) state the
  real policy in both languages: one request 24 h before an enabled deadline, only while that
  instant is still ahead, and **no catch-up alert** if enabled later. Disabling a stored intent
  remains possible after the job closes, with no permission and no deadline.
- Reminder-sheet layout fix: content is now a bounded (`≤85%` height) `SingleChildScrollView` so
  the new policy line does not overflow at 2× text on a 320 px screen. Same items, same order,
  same visual tokens — no Home v2 redesign.

## Notes for captain

1. The guard is per-screen-instance state; there is no global link cache and no cross-feature
   import. A second screen can open the same URL concurrently by design.
2. Fragments are rejected rather than stripped, because a fragment changes which document section
   is presented; the feed should carry the exact URL it wants opened.
3. `ReminderOutcome.permissionError` is an additive enum value. Any exhaustive `switch` outside
   `lib/features` that lists outcomes would need a new case; none exists in the frozen surface.
4. Reminder sheet scrolling: `isScrollControlled: true` plus a bounded child keeps the sheet usable
   at large text; the drag handle and close action are unchanged.
