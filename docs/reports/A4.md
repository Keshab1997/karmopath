## 2. Public API (for captain integration)

```dart
const Duration reminderLeadTime = Duration(hours: 24);

ReminderPlan planReminders({
  required Iterable<Job> jobs,          // current validated feed
  required Iterable<String> selectedJobIds,  // UserPreferences.reminderJobIds
  required DateTime now,               // injected clock
});

DateTime? reminderDeadlineUtc(Job job); // contract deadline rule
String reminderContentKey(Job job, DateTime closesAtUtc); // change detector

ReminderDiff diffReminderPlans({
  required ReminderPlan previous,      // what the platform currently has
  required ReminderPlan desired,       // fresh planReminders(...) result
});
```

* `ReminderPlan.entries` — ordered by `(dueAtUtc, jobId)`; each entry carries
  `jobId`, `dueAtUtc`, `closesAtUtc`, `contentKey`.
* `ReminderPlan.skipped` — ordered by `jobId`, each with a
  `ReminderSkipReason` (`jobUnavailable`, `unsupportedKind`, `notOpen`,
  `noDeadline`, `deadlinePassed`, `optedInTooLate`). `skipReasonFor(id)` and
  `entryFor(id)` are O(n) lookups for UI copy.
* `ReminderDiff.cancellations` (sorted by `jobId`), `.schedules` (sorted by
  `(dueAt, jobId)`, `isReplacement` flags a same-ID replacement), `.retained`,
  `.applyOrder` (cancellations first), `.isNoOp`.
* All collections are unmodifiable; every entry has value equality.

**Localization choice (documented per brief):** the planner emits **no user
copy**. Entries are semantic (`ReminderPlanEntry`) and skips carry an enum, so
the captain composes bilingual strings from the existing feature catalog. The
`contentKey` includes `title_bn`, `title_en` and `organization` so it changes
whenever the alert text would change, but it is a fingerprint — **never a
platform notification ID**, and `Object.hashCode` is not used anywhere.

## 3. Policy implemented (frozen in `docs/BATCH_4.md`)

* One reminder per selected **open recruitment** with a resolvable future
  deadline; `dueAt = closesAt - 24h`; included only when `dueAt > now`.
* `dueAt == now` is **not** new work (equality excluded, tested).
* Late opt-in inside the 24-hour window creates **no catch-up alert**; the skip
  reason distinguishes it (`optedInTooLate`) from a deadline that already passed
  (`deadlinePassed`).
* Skipped without creating an alert: unknown ID, result/admit card, closed,
  withdrawn, no deadline, past deadline, late opt-in. Jobs are never mutated and
  selected IDs/stored preferences are never touched by a skip.
* Deadline rule: exact `applicationEndAt` wins; date-only is inclusive through
  its Asia/Kolkata day, closing at 00:00 IST the next day
  (`2026-11-15` → `2026-11-15T18:30:00Z`). A malformed or impossible date-only
  string (`2026-1-5`, `2026-02-30`) resolves to `null` rather than an invented
  boundary — stricter than the UI helper, never looser.
* `now` is normalised with `toUtc()`, so a non-UTC `DateTime` is compared as an
  instant (tested with `+05:30` inputs).

### Reconciliation

* Keyed by **full job ID**. `previous` = what the platform has applied;
  `desired` = fresh plan. Unchanged entries are retained; new ones scheduled;
  removed/stale ones cancelled.
* An entry is unchanged only when `dueAtUtc` **and** `contentKey` match, so a
  corrected title, a corrected translation, or a moved deadline replaces stale
  text instead of keeping it on the lock screen.
* **Apply order is cancel-before-schedule**, so a replacement for one job ID
  never leaves two live alerts. Cancellations and replacements may share a job
  ID; `ReminderScheduling.isReplacement` makes that explicit.
* Deterministic: both plans are indexed by ID, outputs are sorted and
  duplicate-free, and re-running reconciliation on the applied result is a
  no-op (`isNoOp`, `retained` = all entries). Input order does not affect output.
* A duplicate job ID inside one plan throws `ArgumentError`: a real feed cannot
  contain one (the contract parser rejects it), so silently choosing is worse
  than failing loudly.

## 4. Truthful limits

* A plan is **intent, not delivery**. Nothing here proves a notification was
  scheduled, survived a reboot, or fired; the captain owns the plugin, stable
  persistent platform IDs, permission state and timezone handling.
* OS state, restart reconciliation, permission denial and Android background
  restrictions are **not modelled** — by design (`docs/BATCH_4.md`).
* Removing a scheduling intent says nothing about OS cancellation; the diff
  expresses the desired change, the platform performs it.
* No persistence: the captain must store the applied plan (or its entries) to
  feed `previous` on the next run. The `contentKey` is exactly what should be
  persisted alongside each platform ID.

## 6. Integration notes

1. **Wire-up:** `final desired = planReminders(jobs: feed.jobs,
   selectedJobIds: preferences.reminderJobIds.value, now: clock());` then
   `diffReminderPlans(previous: storedPlan, desired: desired)`, apply
   `applyOrder` (cancel → schedule) through the platform, and persist the desired
   entries + allocated platform IDs as the next `previous`.
2. **Store the content key.** Without it a corrected title cannot be detected;
   re-deriving it later is not equivalent to storing what was actually applied.
3. **Explain skips.** `skipReasonFor(id)` maps directly onto user copy for
   "reminder pending / no alert because …" — including the required 24-hour
   policy sentence for `optedInTooLate`.
4. **Do not persist `generatedAtUtc` as state**; it is only the decision instant.
5. `deadline_rule_consistency_test.dart` imports
   `lib/features/common/formatting.dart` **read-only** to prove the two deadline
   resolutions agree. If you prefer zero cross-layer tests, deleting that one
   file changes nothing in the planner; if you prefer one rule everywhere, moving
   `reminderDeadlineUtc` up into a shared place later is a mechanical change.
