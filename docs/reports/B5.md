## What changed

### Eligibility rule (`lib/features/common/reminder_controller.dart`)

- New `reminderDueAtUtc(closesAtUtc)` = `closesAtUtc - 24 h`, and
  `reminderWindowOpen(info, now)`: a **new** request is accepted only while the job is open and
  `now` is **strictly before** the due instant. At equality the reminder is already due, so it is
  too late. Arithmetic only — the closing instant still comes from the existing
  `deadlineInfo`/date-only IST semantics; no data-layer import, no second clock.
- New outcome `ReminderOutcome.tooLate`, greedy order for enabling:
  supported deadline → closed/withdrawn → 24 h cutoff → permission prompt → **re-evaluate all
  three** against the current fields and the current clock → persist. Nothing is requested and
  nothing is stored when refused, and the refusal is a value, not an exception.
- Disabling is untouched: it is decided before any of this, needs no permission, no deadline and
  no open window, so a stored intent can always be removed after closure, lateness or a
  correction.
- `reminderOutcomeMessage` maps `tooLate` to the new copy; the seven outcomes still produce seven
  distinct messages.

### Truthful stored-intent state (`lib/features/common/reminder_intent_state.dart`, new)

- `StoredReminderState { pending, duePassed, closed, withdrawn, unavailable, noDeadline }`
  derived from the job's **current** fields and the current clock.
- `storedReminderMessage(state)` / `reminderRowSubtitle(job:, now:, lang:)` produce the only
  assertions the app can honestly make: the request is *stored*. A pending row reads
  “Stored request · <deadline label>”; a due-passed or closed row says the deadline/reminder time
  has passed and that **whether a notification appeared is unknown**; withdrew/unavailable say the
  stored request is still listed. No label claims scheduled, delivered or missed, and no stored id
  is cleared on a rebuild.

### Screens

- Detail (`job_detail_screen.dart`): computes `lateForReminder` from the live ticker clock and
  keeps the enable control **tappable** in that state, showing the reason inline and again as a
  snackbar on tap (closed and no-deadline keep their existing disabled control with inline
  explanation, because there the state cannot change by waiting). A stored intent shows its current
  state under the control.
- Home reminder sheet (`home_screen.dart`): every row now renders `reminderRowSubtitle`, so stored
  intents are described by the job's present situation. Sheet bounds, drag handle, close action and
  Home v2 layout are unchanged.
- Ticker (`deadline_clock.dart`): `deadlineWatchInstants` also yields `closesAt - 24 h`, so the
  enable control becomes “too late” at the cutoff while the page stays mounted, without polling.
  Captain’s fresh-clock regression test is untouched and still green.

Shared surfaces untouched: `AppActions`, `UserPreferences`, `Job`, the screen constructors and
`setReminderIntent`’s parameters are unchanged (the two new optional callbacks were already added
in batch 3). No scheduler status is invented — the captain still owns delivery.

## Notes for captain

1. `ReminderOutcome.tooLate` is an additive enum value; any exhaustive `switch` outside
   `lib/features` that lists outcomes would need a case (none exists in the frozen surface).
2. A stored intent whose window has closed is **kept**, not auto-removed: removing it would be a
   silent write the user did not ask for. The sheet and detail explain it until the user turns it
   off.
3. Detail keeps the enable control enabled in the late state on purpose: a disabled button with no
   feedback hides the reason. Closed and no-deadline stay disabled with their existing inline
   copy, which their existing tests pin.
4. The 24 h cutoff is now a ticker instant, so a page left open flips to “too late” exactly on
   time; calendar bells are unchanged (they mark an enabled reminder, not a schedule).
