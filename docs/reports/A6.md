## 2. Public API

```dart
abstract class ReminderPlatform {
  Future<void> cancel(int id);
  Future<void> schedule(ReminderPlanEntry entry, int platformId);
}

class ReminderApplier {
  ReminderApplier(ReminderStateStore store);

  Future<ReminderApplyResult> apply(
    ReminderPlan desiredPlan,
    ReminderPlatform platform,
    String payloadVariant,
  );

  Future<ReminderApplyResult> applyDiff(
    ReminderDiff diff,
    ReminderPlatform platform,
    String payloadVariant,
  );
}

class ReminderApplyResult {
  List<String> cancelledJobIds;            // recorded cancellations, in order
  List<ReminderPlanEntry> scheduledEntries; // recorded schedules, in order
  List<ReminderApplyFailure> failures;      // per-job, in encounter order
  bool get isNoOp;
  bool get isFullySuccessful;
}

class ReminderApplyFailure {
  String jobId;
  Object error;                    // ReminderStateException or platform error
  StackTrace stackTrace;
  bool duringCancellation;
  ReminderStateFailure? get stateFailure;  // set when the ledger failed
}
```

The store is used verbatim, exactly as A5 defined it:
`reserve(String jobId)`, `recordSchedulingSuccess({required entry, required
payloadVariant})`, `recordCancellationSuccess(String jobId)`. There is
deliberately still no "mark whole plan applied" path anywhere.

## 3. How an apply works

`apply()` reconstructs the previously-applied plan from
`ReminderStateStore.snapshot` (rows with non-null `applied` only — a bare
reservation means "allocated, never recorded as scheduled") and diffs it
against the desired plan with A4's `diffReminderPlans`. `applyDiff()` takes a
caller-computed diff as-is. Both then execute the same two phases:

1. **Cancellations first** (diff order: by job ID), each followed immediately
   by `recordCancellationSuccess(jobId)` — and only after the platform
   reported success.
2. **Schedules second** (diff order: due time, then job ID), each preceded by
   `reserve(jobId)` and followed, only on platform success, by
   `recordSchedulingSuccess(entry: entry, payloadVariant: payloadVariant)`
   with the exact plan entry and the captain's variant passed through
   untouched.

Consequences, all covered by tests:

- **Stable IDs.** A replacement cancels and reschedules under the same
  reserved ID; a removed-then-readded job reuses its retained reservation;
  IDs are never derived from `hashCode`, never truncated, never freed.
- **Exhaustion is terminal.** At `maxPlatformId` (2147483647) the last ID is
  handed out; the next new job fails per-job with
  `ReminderStateFailure.exhausted`, schedules nothing, writes nothing, and
  never wraps. A job that already holds a reservation can still be
  rescheduled after exhaustion, because `reserve` returns it without
  allocating.
- **Per-job failures, never whole-plan marking.** A throwing platform method
  or a failing ledger write leaves that job's ledger value exactly as it was
  (A5 writes-then-publishes), appears in `failures` with its phase
  (`duringCancellation`), and does not stop later jobs. One deliberate
  coupling: if the cancellation half of a replacement fails, that job's
  schedule is skipped in the same apply — the next apply regenerates the same
  diff from the ledger and retries the pair, which the tests demonstrate.
- **Variant freshness.** A retained entry whose recorded `payloadVariant`
  differs from the one passed to `apply()` becomes a cancel+schedule
  replacement under the same ID, so a language or copy-version switch never
  leaves stale text scheduled. `applyDiff()` does not reinterpret retained
  entries.
- **Unknown jobs are ignored.** A cancellation for a job with no reservation
  (or nothing applied) has no known platform ID and is skipped silently.
- **Serialisation.** `apply`/`applyDiff` enqueue synchronously onto one
  queue per applier, so concurrent calls execute strictly in call order;
  the store's own queue serialises the underlying read-modify-writes.
  Duplicate platform IDs are therefore impossible, and two identical
  concurrent applies schedule each job exactly once (the second diffs
  against the first's committed state and becomes a no-op).

`apply` throws only when no job could be processed safely: a blank
`payloadVariant` (`ArgumentError`, before touching anything) or a ledger that
cannot be loaded (`ReminderStateException`, e.g. `unreadable`/`corrupt`), in
which case the platform is untouched and nothing is written.

## 4. Crash window and retry semantics (unchanged from A5, now exercised)

The OS accept and the ledger record are still two systems. If the process
dies — or the record write fails — after the platform accepted an operation,
the result carries a per-job failure whose phase says which half is
unrecorded, and the ledger keeps publishing its previous value. Recovery is
deliberately boring: call `apply` again with the same desired plan. The diff
is regenerated from the ledger, the same stable ID is reused, the platform
operation repeats (captains should implement `cancel`/`schedule` to be
idempotent per ID), and the record lands. On process start the captain must
still reconcile the ledger against the OS pending-notification list before
trusting either side; a ledger entry remains a record of reported intent,
not a delivery receipt.

## 6. Integration notes for the captain

1. Implement `ReminderPlatform` over the chosen notification plugin:
   `cancel(id)` must succeed when nothing is pending under `id`, and
   `schedule(entry, platformId)` should replace any pending notification
   under the same ID. Build the notification copy from `entry` plus the
   active language at schedule time; the data layer never sees copy.
2. Keep one `ReminderApplier` over the app-lifetime `ReminderStateStore`;
   call `apply(desiredPlan, platform, '$language@copy-$copyVersion')`
   whenever the plan from `planReminders` or the variant changes. Surface
   `result.failures` as a retry affordance; a throw means the ledger itself
   needs attention first.
3. `await store.initialize()` during startup remains required, and on start
   reconcile the ledger against the OS pending list (see §4) before the
   first apply.
4. Permission prompting stays outside this module: request it before calling
   `apply`, and treat a denial as "do not call yet", not as a per-job
   failure.
