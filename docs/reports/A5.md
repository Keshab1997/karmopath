## 2. Storage shape

One key — `karmopath.reminder_state.v1` — holds **one** schema-versioned JSON
string, written as a **single-element string list**, so registry rows and applied
metadata cannot tear across keys or across writes:

```json
{
  "schema_version": 1,
  "next_platform_id": 3,
  "entries": [
    {
      "job_id": "wb-police-constable-2026",
      "platform_id": 1,
      "applied": {
        "due_at": "2026-11-19T12:00:00.000Z",
        "closes_at": "2026-11-20T12:00:00.000Z",
        "content_key": "…A4 fingerprint…",
        "payload_variant": "bn@copy-3"
      }
    },
    { "job_id": "wb-health-2026", "platform_id": 2, "applied": null }
  ]
}
```

`schema_version` lives **inside** the document, so the key name and the document
version can never disagree.

## 3. Public API

```dart
class ReminderStateStore {
  ReminderStateStore({required PreferencesStore store});
  static const String storageKey = 'karmopath.reminder_state.v1';

  Future<void> initialize();                       // idempotent, retryable
  ValueListenable<ReminderState> get state;        // immutable snapshots
  ReminderState get snapshot;
  bool get isInitialized;

  Future<ReminderReservation> reserve(String jobId);
  Future<void> recordSchedulingSuccess({required ReminderPlanEntry entry,
                                        required String payloadVariant});
  Future<void> recordCancellationSuccess(String jobId);
  void dispose();
}
```

`recordSchedulingSuccess` takes an A4 `ReminderPlanEntry` (so `jobId`,
`dueAtUtc`, `closesAtUtc`, `contentKey` come from the planner unchanged) plus the
captain's opaque `payloadVariant`. There is deliberately **no** "mark this plan
applied" method: only per-job, per-operation reports are accepted.

## 4. Rules implemented

**Allocation.** IDs are `1..2147483647` (signed 32-bit), handed out
monotonically from the persisted counter, never reused after cancellation, never
wrapped, never derived from `hashCode` and never truncated. `reserve` writes the
reservation **before** returning; a failed write allocates nothing. Repeating a
reservation for the same job returns the stored ID without a write. Exhaustion
(when `next_platform_id` passes `2147483647`) fails with
`ReminderStateFailure.exhausted` and changes nothing.

**Validation on load.** Rejected with a precise failure instead of being
repaired: invalid JSON / non-object root / empty string / zero or several
elements / wrong field types / a job ID that is not a `[a-z0-9-]{1,100}` slug /
a platform ID outside `1..2147483647` / a missing `applied` key / a non-`Z`
timestamp / `due >= closes` / empty `content_key` / empty `payload_variant`
(`corrupt`); duplicate job IDs, duplicate platform IDs, and any allocated ID not
strictly below `next_platform_id` (`inconsistent`); an unsupported
`schema_version` or a missing one (`unknownSchema`); a throwing store (`unreadable`).
Unknown *extra* keys are tolerated for additive forward compatibility — an
unknown schema version is not.

**No silent reset.** `null` (key never written) is the only "empty". Every
mutating operation awaits `initialize()`, so an unreadable or corrupt document
blocks all writes rather than being overwritten. No migration, no auto-repair.

**Applied ledger.** `recordSchedulingSuccess` requires an existing reservation
(`unknownReservation` otherwise — it never creates one implicitly) and a valid
entry; instants are normalised with `toUtc()` and stored with an explicit `Z`.
Recording an identical application is a no-op write. `recordCancellationSuccess`
clears the applied metadata and **keeps** the reservation and its ID; on a job
with no reservation or nothing applied it is a no-op.

**Failure discipline.** A write is committed to the store first and published to
`state` afterwards, so a failing store leaves both the durable document and the
in-memory snapshot on their previous value and the caller gets
`ReminderStateFailure.storage`. Every read-modify-write runs through one queue,
so concurrent callers cannot duplicate an ID or lose each other's entries; the
queue is re-armed after an error, so a retry works.

**Isolation.** Only `karmopath.reminder_state.v1` is ever read or written;
`karmopath.saved.v1`, `karmopath.reminders.v1`, `karmopath.feed.v1` and
language settings are untouched (asserted).

## 5. The crash window this module cannot close

Scheduling spans two systems: the OS accepts a notification, then the ledger is
written. If the process dies in between, the OS holds a notification the ledger
does not know about; the mirror case exists after a cancellation. No local
bookkeeping can make that atomic, and this module does not pretend to: there are
no fake transactions, no optimistic "assume applied" and no platform stubs that
report success. **On start-up the captain must reconcile the ledger against the
OS** (query/cancel pending notifications) before trusting either side.

A ledger entry records that the platform reported an application. It is **not**
a delivery receipt and not evidence that a notification was ever displayed.
Permission state, scheduling results, reboot persistence and delivery remain
captain-owned and unproven here.

## 7. Integration notes

1. `await ledger.initialize()` during startup, before rendering reminder state;
   a throw here is a real problem to surface, not an empty registry.
2. Flow per job: `reserve(jobId)` → schedule through the platform → only then
   `recordSchedulingSuccess(entry: planEntry, payloadVariant: lang@copyVersion)`.
   For removals: apply the cancel → only then `recordCancellationSuccess(jobId)`.
3. Persist nothing else; `contentKey` + `payloadVariant` are exactly what make a
   later correction detectable.
4. Reconcile against the OS on start-up (see §5) and treat a ledger entry as
   intent-that-was-applied, not as proof of delivery.
5. Reservations are permanent for the life of the document. That is what makes
   ID reuse impossible; if the registry ever needs pruning (e.g. thousands of
   dead jobs), that is a captain-owned policy with its own safeguards, and this
   module will not do it silently.
