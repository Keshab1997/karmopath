### HttpFeedTransport behaviour

* **Configuration is validated at construction.** Non-HTTPS, empty host, embedded
  `user:pass@` credentials, a `#fragment`, `timeout <= 0` or `maxBytes <= 0`
  all throw `ArgumentError`, so a misconfigured URL fails at composition time
  rather than leaking a secret at request time. The fragment rule is an extra
  guard beyond the contract wording and is documented in the class.
* **Exactly one GET, no retries.** Header `accept: application/json`; no
  `authorization`, `cookie` or proxy-auth header is ever set. The injected client
  is owned and closed by the caller: the transport never calls `close()`
  (asserted in tests on both success and failure paths).
* **Status.** Only HTTP 200 is accepted; any other status fails with the code
  preserved for logging, and the response body is discarded immediately.
* **Two byte caps.** The declared `Content-Length` is rejected before reading
  when it already exceeds `maxBytes`; the number of bytes actually streamed is
  counted independently, so a chunked response that declares nothing (or lies)
  is still stopped. The subscription is cancelled the moment the cap is crossed
  and the rest of the body is never read.
* **Strict UTF-8.** `utf8.decode(..., allowMalformed: false)`; malformed bytes
  fail the fetch instead of becoming U+FFFD text that could be cached as if it
  were reviewed content. Verified: a leading UTF-8 BOM is consumed by Dart's
  decoder (documented in the test, not assumed).
* **Total timeout.** One budget covers send + headers + body: the body timer is
  the remaining time after the headers arrive. No automatic or bounded retry.
* **Resource cleanup.** Exactly one subscription per fetch, cancelled on status
  failure, declared oversize, streamed oversize, body timeout, stream error and
  a synchronously throwing client. A response that arrives *after* the header
  timeout is drained and cancelled so its socket is released.
* **Web-safe imports only.** `dart:async`, `dart:convert`, `dart:typed_data`,
  `package:http`; no `dart:io` anywhere in `lib/data/platform` (asserted by a
  source check in the test suite).
* **No trust.** The payload is returned as raw text; JSON/schema validation
  stays in `CachedJobRepository`/`JobFeed`.

### Timeout semantics (asked explicitly by the brief)

The timeout **stops waiting and cancels the local response-stream subscription**.
It **cannot abort an in-flight request**: `package:http` exposes no abort API for
a caller-owned `Client`, and this class deliberately does not close the client.
After a timeout the underlying socket/browser request may keep running until the
server finishes or the app closes the client; nothing in the app reads or
buffers its bytes, and a late response is drained and cancelled explicitly.

### Browser limitations (stated as limits, **not** runtime-proven)

* Only `flutter analyze` proves the web import surface. No web build, browser
  run or manual CORS check was performed (builds are forbidden for workers).
* On web, redirects and the transfer itself are the browser's; `BrowserClient`
  (http 1.6.0) exposes `content-length` only if the response carries it —
  it is CORS-safelisted, but it is absent for chunked responses and it describes
  the *compressed* size when the server gzips, so the streamed counter is the
  authoritative cap and the declared check is only a fast pre-filter.
* A cancelled body does not necessarily abort the browser's own download.
* With `package:http` on web the body is read after the browser has buffered it,
  so the cap protects Dart's memory use, not the browser's.
* `shared_preferences_web` 2.4.3 (pinned transitively) backs
  `SharedPreferencesAsync` with `window.localStorage`: subject to the browser
  quota (order of 5 MB) and to storage being cleared with site data. The 2 MiB
  feed cap fits, but eviction is not an error the app can prevent.
* Android/iOS persistence, background behaviour and real-device timeouts are
  **NOT RUN** — no device or emulator in this sandbox.

## Observations for the captain (not changed here)

1. `CachedJobRepository` maps *every* transport failure (HTTP 503, oversize,
   invalid UTF-8, socket) onto its two "offline" strings. That is batch-1
   wording, outside this brief; a distinct "server did not answer properly"
   message would be more accurate if you want it.
2. Dispose order at app shutdown: close your `http.Client` **after** disposing
   the repository, so an in-flight fetch is not cut mid-stream.
3. Reminder scheduling must read `reminderJobIds` only after
   `LocalUserPreferences.initialize()` resolves; the store never fabricates an
   empty set on a read error (it throws), so a failed load can be retried rather
   than being mistaken for "no reminders".
