Branch: `agent/C/publish-check-v1` (from origin/main `4ca4156`, which contains frozen base `2f4ae45` plus the Batch 6 dispatch docs). No merge to main, no rebase/force-push, no tags/releases/workflow dispatch.

## What was built

- `tools/feed/check_publish.py` — offline, read-only publish-readiness CLI. It runs the **unchanged** `validate.py` rules first (`validate.validate_feed` is imported; rules are never forked), then adds per-job checklist items: `source_url`/`notice_url` nonempty absolute HTTPS without credentials **and without fragment** (fragment rule is additive; the other link rules are the validator's own, invoked via `validate._https_url`), `published_at` present/valid/not in the future using the same 5-minute clock tolerance as the validator, and at least one `districts`/`qualifications` entry where applicable (empty arrays → `[WARN]`, non-blocking by default, `--strict` fails warnings). Rejects with actionable field paths + job IDs; prints `[PASS]/[FAIL]/[WARN]` lines in deterministic job/field order, a counts summary, and `RESULT: READY|NOT READY`. Exit 0 only when validation and all checklist failures pass. Flags: `--now <UTC Z>` for deterministic reruns, `--strict`. No network, no Git writes, no upload, no publication.
- Admin panel (`admin/app.js` + `admin/index.html`): after a candidate export **validates**, the preview column shows a read-only publish-checklist panel with the same per-job checks and pass/fail counts, labeled as a snapshot of that export (with export timestamp). It never blocks an export validation already allowed, never auto-approves, and does not update on later edits; a blocked/invalid export hides it, and import replacement or storage recovery clears it. Existing dirty-tracking, review guards, and export gating logic are untouched (only an added sentence to the success feedback).
- `admin/admin-core.js`: new pure, dependency-free `httpsLinkIssue()` + `publishChecklist(jobs, nowMs)` shared by UI and Node tests (same checks/tolerance as the CLI).
- `admin/README.md`: handoff chain documented — **export → validate → compare (if baseline) → checklist → human verify source/dates → owner-authorized publication (separate step)**; CLI usage, exit codes, determinism, panel behavior, and the read-only/no-auto-approve boundary.

## Limitations

- Real-browser smoke (Chromium) NOT RUN here; the fake-DOM Node suite and syntax checks are the executed evidence for the panel.
- The checklist (CLI or panel) proves structure and offline readiness signals only. It cannot establish that a source URL is genuinely official, that notice contents match the summary, or that dates/eligibility are correct.

## Manual publication boundary

`RESULT: READY` is not an approval and not a publication. After a READY result a human must still review the original source and notice for every new/changed item, inspect comparison output and withdrawals, and only the separately authorized feed owner may hand the approved artifact to the existing publication process (with its own rollback/cache plan). Neither the CLI nor the admin panel contains any upload, publish, or network action.
